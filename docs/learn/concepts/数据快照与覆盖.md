# 数据快照与覆盖

数据快照是采集系统截至某个版本保存的记录集合，不保证包含平台全部历史。覆盖指哪些对象、时段和关系能够被这套采集过程观察到。本研究必须先核对覆盖，才能判断“没看到回复”是可见范围内未发生，还是观察时间不足或记录缺失。跨月比较尤其要防止把采集规则变化解释成账号行为变化。

## 四种时间不能互换

| 时间 | 回答的问题 | 误用示例 |
|---|---|---|
| `created_at` | 内容什么时候创建？ | 不能证明随后一直有抓取 |
| `updated_at` | 记录声明何时修改？ | 不是每次点赞或状态变化的完整历史 |
| `_scraped_at` | 记录何时被采集？ | 10月抓到旧帖不等于10月发帖 |
| 快照版本日期 | 这一批数据以哪个版本发布？ | 不保证每个线程都观察到该日 |

最终记录里的点赞、karma等状态，也不能当作内容创建当时的值。所有分析窗口统一写UTC，避免日期边界错位。

## 当前输入及其限制

本项目使用jscmp4/Moltbook的2026-10-07快照。[已有数据核查](../../notes/当前数据核查-2026-10-23.md)记录合并表为3,699,521条帖子、19,728,495条评论；这是项目既有审计，本页没有重跑计数。

数据卡片明确说明以下限制：

- 评论是否被抓取与帖子计数门槛、日常采集及后续回填有关，不能假定每帖具有相同入样机会。
- 3月起原始`depth`未观察到大于5的评论。不能区分更深回复被隐藏还是无法发表；重建父链也不能恢复从未返回的节点。
- 本版本`agent_snapshots`重复首次观察资料，不能作为karma或粉丝增长面板。

这些是本项目数据源的限制，不能写成另一篇论文所用数据的事实。卡片也会更新，引用时应保存所核版本。

## 按顺序检查完整性

先检查ID唯一性、评论所属帖子、父评论是否存在及同帖、时间顺序，再检查账号是否可识别。随后比较存储评论数与API的`comment_count`，并按创建月份、采集方式报告差异。

计数相等只说明两个数一致，不证明内容和关系完整。计数不等也不全是爬虫漏采：卡片说明有些计入总数的评论不被接口返回。不要直接用“已存数／计数”作逆概率权重，因为它不是已知的入样概率。

## 将观察问题与行为结果分开

缺父、缺帖、缺账号分别保留原因；不改接帖子、不合并为“unknown”账号。删除占位评论可以保留结构信息，但正文不可判；内容分析排除它们时，不能顺带抹去后代的真实父链。

随访时间不足接着按[右删失](右删失.md)处理；足够日历时间仍须检查覆盖。结果应写“本快照中的可观察账号／线程”，并附版本或文件清单、哈希、字段字典与排除流程。
