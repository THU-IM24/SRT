# 05 按时间窗比较对话持续

**目标**：把“会不会回应”和“有回应时多快”分开，建立可比较的批次。
**先读**：[右删失](../concepts/右删失.md)、[时间衰减](../concepts/时间衰减.md)、[生存分析](../concepts/生存分析.md)。

## 1. 先写估计对象

主问题示例：在有可靠父关系、创建后至少观察24小时的非帖主评论中，帖主在24小时内直接回复的比例是多少？另报有回复者的等待时间分位数。

单位是候选评论。不要把“有回复者的中位等待时间”说成全部评论的回应能力。若同时研究7天跨帖再接触，另建账号对为单位的表，不混入同一个分母。

## 2. 选择可靠终点

数据创建时间的最大值只能提供观测边界线索，不能证明之前所有评论都完整。先读审计和数据卡片，对刷新/回填差异做检查。练习可以保守取`2026-10-06T00:00:00Z`为分析截点，并明确这是人为分析截点，不是已证明覆盖终点。

对于24小时窗，候选评论应早于截点减24小时；对7天窗应早于截点减7天。所有回应也限制在截点以内。敏感性分析把截点再提前1天、7天。

## 3. 构造事件时间

沿04的父子表，取每条候选评论之后最早的、作者符合目标条件的直接回复。应检查：父子同帖、作者非空、`child_ts>parent_ts`。如果研究任何人回复，结果与“帖主回复”不同；两者分别命名。

```sql
SELECT parent.id,
       min(child.ts) FILTER (WHERE child.ts>parent.ts) AS first_reply
FROM candidates parent
LEFT JOIN all_thread_comments child
  ON child.parent_id=parent.id AND child.post_id=parent.post_id
GROUP BY parent.id;
```

这里是设计SQL，不可直接运行：`candidates`与`all_thread_comments`需先按上述规则创建。使用完整父子查找，避免在切窗时把早期父节点删掉。

## 4. 固定窗基线

记录`eligible_24h`、`replied_24h`、`wait_seconds`。无回复但有完整24小时观察的样本可以记`replied_24h=0`。无足够随访或父关系不可解析的样本记为不合格，不是0。

分别按月、线程规模、平台spam标记与账号活动层报告比例和分母。在同一候选集合下，再对已回复样本给p25/中位数/p75。对最小样本过少的层不作强解释。

## 5. 保留未回复者的生存分析

若不同随访时长都要保留，构造`duration=min(reply_time,cutoff)-parent_time`和`event`标记。Kaplan–Meier只在删失近似独立且覆盖合理时解释为回复时间分布。中位数没达到时写“未达到”，不能拿最快一半已回复者代替。

本教程没有安装额外生存包，也没有声称已跑出该模型。后续实施前先在人工核对的候选表上验证，再增加依赖。

## 6. 长期比较怎样控制构成

不要把1月所有新账号与9月存活账号直接对比为“学习进步”。同时比较固定月批次、固定活跃账号面板和新进入账号，控制前期活动、语言、社区及帖龄。失活和选择进入仍可能影响结果。

03的指令变化、Eziz的持续性研究都可提供假设；它们没有让当前快照自动具备因果识别。制度前后只作描述，除非补足真实发布时间、采用日志和合适对照。

## 7. 最低交付

交一张含资格分母、回复比例、条件等待分位数、不可解析率、截点敏感性的表。对话持续已有直接论文，本项目是否有增量见[下一步研究计划](../../notes/下一步研究计划.md)。
