# 06 抽样与人工编码对话功能

**版本**：2026-10-30 复核版
**目标**：建立可复核的父消息—子回复样本，检验结构上的回应是否真正承接内容。
**先读**：[抽样设计](../concepts/抽样设计.md)、[内容编码与一致性](../concepts/编码一致性.md#内容编码单位标签与手册)。

## 1. 先定义总体，再抽样

热门、大、深的线程容易找到“好对话”，但不能代表全体。建议目标总体定义为：父关系已解析、正文可读、时间合格的真实父子对。

- 顶层评论的父消息是帖子正文；楼中楼的父消息是父评论。
- 缺少必要上下文先记 `context_sufficient=否`，不能强行判无承接。
- 分层候选包括月份、线程规模、是否涉及帖主、层级、语言和平台标记。
- 分层不要过多；先选4–8个与主问题最相关、每层能抽到足够样本的层。

抽样 SQL、随机种子、每层总体数 `N_h` 和样本数 `n_h` 要随结果保存。不要从公开热门榜手工挑例子后再称为总体估计。

## 2. 第一轮试标

建议80–120对、两名编码员独立试标。这是工作量起点，不是已经完成的样本，也不能直接当作正式功效计算。每条使用随机 `item_id`，不在共享表里保留账号标识：

| 字段 | 允许值或说明 |
|---|---|
| `context_sufficient` | 是／否 |
| `response_function` | 回答、补充、反驳、澄清、确认、社交、推广、其他 |
| `semantic_uptake` | 是／否／不可判 |
| `new_information` | 是／否／不可判 |
| `template_like` | 是／否／不可判 |
| `parent_anchor` | 父消息的具体内容点 |
| `child_evidence` | 子回复对应的证据片段（脱敏） |
| `coder_id` / `rubric_version` | 编码员和手册版本 |

示例文本用自编例子。不要把凭证、联系方式、原始账号或不必要的整段正文放进共享仓库。

## 3. 怎样判断承接

父消息“数据只能占1GB内存，怎样统计？”与子回复“用 DuckDB 逐列扫描并设置 `memory_limit`”可判承接；“智能体社区发展很快”只是同属技术话题，不承接。单独的“谢谢”可能是社交确认，不能自动判为针对性回应。

若需要祖先消息，最多固定增加两层上下文并记录补充次数。无法理解语言、上下文缺失或文本不可读记“不可判”，不要让编码员私自机器翻译后当作原语义。

## 4. 独立一致性先于共识

先保存两名编码员的原始标签，再计算一致率、κ或α、混淆矩阵和各类样本数；最后才讨论分歧和共识。先讨论统一、再声称独立一致率100%是错误的。

试标后可以修订定义，但要冻结 `rubric_version`。正式验证集与试标分离；同一线程内高度相似的评论不要跨训练和测试，避免复制泄漏。稀有的“反驳”类要检查是否有足够样本，而不是只看总体准确率。

## 5. 真实父子与错配父子

可为部分子回复匹配同月、同语言、相近长度和主题的其他父消息，隐藏真假分组后让编码员同样判断。错配对不天然是负标签，偶然匹配也可能有承接，因此报告为对照条件，不强行解释为“无承接”。

比较两组承接率和区间；若真实对并不优于错配，说明同主题线索可能已解释大部分结果。即使真实对更好，也只是文本依赖证据，不是内部理解的直接证明。

## 6. 正式样本与总体估计

预算允许时再扩到约600–1000对，具体数量由试标比例、聚类程度和目标精度决定。深线程过抽样时用 `N_h/n_h` 做层权重，并另报等线程、等账号和评论权重结果。按线程或账号 bootstrap，不能把同一帖的数百条评论当作完全独立。

最低交付包括：编码手册、抽样 SQL、入样概率、独立标签、分歧处理、加权规则和脱敏汇总。当前项目尚未完成这些人工结果；本教程写的是执行规范，不是研究发现。

## 7. 大模型辅助的进入条件

先用独立人工集评价每一类，再决定是否扩标。冻结 prompt、模型和版本、上下文格式、随机种子、失败重试和判定阈值；把模型输出当作待验证标签。付费调用、整批上传原文、部署大模型和向真实平台发帖都不在本教程自动执行范围。
